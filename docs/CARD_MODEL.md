# 공통 카드 모델 초안

요약: 논문 사실·출처와 프로젝트별 적용 판단을 분리하고 안정 ID로 연결한다. 연구 비교와 실험 조언의 다른 조건을 담으며 draft-2 구현과 이후 설계 제안을 구분한다. 안정 호환성 계약은 아직 없다.

현재 논의 기준은 아래 [첫 버전 최소안](#첫-버전-최소안)이다. 앞선 독립 Evidence 객체·record_status·구조화 context_refs는 확장 비교안이며 첫 버전 필수 필드가 아니다.

첫 CLI의 기계 검사는 [card.schema.json](../schemas/card.schema.json)이 소유한다. draft-2를 읽고 ID·참조·판본·페이지 범위를 검사하지만 원문 의미나 확인 이력의 진실성은 보증하지 않는다. 입력을 다시 쓰지 않아 미지 필드·주석·본문은 그대로 내보낸다. workspace 연결은 [CLI 사용법](CLI.md)을 따른다.

## 첫 버전 최소안

현재 CLI의 draft-2 필드는 [공개 schema](../schemas/card.schema.json)와 [합성 예제](../examples/minimal/workspace.json)로 확인한다. 아래의 초기 확장 모델·검토안은 구현된 필드와 구분한다. 안정 버전이나 외부 소비자가 생기면 변경·마이그레이션 절차를 다시 정한다.

| 단위 | 처음 등록할 때 | 실제 근거로 사용할 때 | 본문에 남길 것 |
| --- | --- | --- | --- |
| Paper | ID, 문서 제목, 원문 위치(URL 또는 기존 파일), review.status=draft | 확인한 판본, claims의 ID·요지·locator, 현재 검토 상태 | 조건·한계, AI 해석, 이전 확인 이력과 원래 기록 링크 |
| Application | ID, 프로젝트 ID, claim_refs, decision.status=proposed | 연결된 주장·프로젝트 맥락·판단 이유 | 현재 질문, 관찰, 기존 실험 링크, 다음 확인 |

`schema_version`·`type`·ID는 도구가 생성하는 관리 정보로 두고 사용자가 매번 입력할 양식으로 만들지 않는다. 문서 첫 제목을 목록 이름으로 사용하여 label을 중복 관리하지 않는다. 공식 서지 제목이 확인되면 가져올 수 있지만 모르는 제목을 생성하지 않는다.

Paper에 아직 읽지 않은 논문을 등록할 수 있다. claims는 없거나 빈 목록이어도 되지만, 이를 검토된 근거처럼 내보내지 않는다. 새 Application에는 선택한 Paper 안의 실제 claim ID가 필요하다. 미완성 작업 메모 저장과 검토된 근거 내보내기 검사는 구분한다.

최소안은 한 Paper 기록이 확인할 원문 판본 하나를 가리키고 claim 안에 locator를 둔다. 별도 source ID·evidence ID와 연결 배열은 제거한다. 페이지·절은 별개 locator로 유지한다. 다른 판본이나 여러 자료를 함께 근거로 써야 하면 덮어쓰지 않고 판본/근거 모델 확장을 먼저 검토한다. 실제 사용처에서 다대다 근거 공유가 필요해지는 것이 확장 계기다.

이 최소안의 claims는 **저자가 보고한 내용**으로 한정한다. 따라서 kind를 생략할 수 있다. AI 해석은 표시된 본문 절, 프로젝트 관찰은 Application에 둔다. 종류 구분 자체를 없앤 것이 아니다.

Application의 question·context_refs·reference_base는 필수가 아니다. 질문과 역할을 설명한 실제 Markdown 링크를 본문이 소유한다. 첫 버전에서 링크를 역할별로 자동 수집·검사한다고 약속하지 않는다. decision.action은 방향이 정해졌을 때만 추가하며 누락은 미정이다. decision.status는 proposed/accepted로 유지하고 accepted에는 실제 결정 근거가 필요하다.

## 다중 주장·표·다른 수치 적용

같은 표를 여러 주장이 참조할 수 있고 한 주장에 여러 표 locator를 둘 수 있다. 표별 보고값은 요지에서 어느 표의 값인지 구분하며 페이지 대응이 불분명하면 임의로 합치지 않는다.

다른 실험의 숫자는 조건과 함께 별도 주장으로 둔다. 같은 항목의 보고값 불일치는 양쪽 값·위치를 보존하고 본문에 미해결로 남긴다. 자동으로 정답을 선택하거나 평균내지 않는다. 수치·단위·표본·조건을 자동 비교할 데이터셋은 아직 아니다. 그 기능이 실제 필요해지면 값·지표·단위·조건·근거를 함께 구조화한다.

본문 전체를 동반하는 현재 읽기 흐름에서는 별도 conflict 객체·claim별 review·details_ref를 추가하지 않는다. 전체 review가 draft인 동안 일부 주장도 검토 완료로 자동 승격하지 않는다. 이후 검토 완료한 주장만 따로 내보내거나 본문 일부를 선택해야 할 때 주장별 상태/본문 연결의 필요성을 다시 판단한다.

## 이전 확인 이력과 현재 검토 상태

상태 필드는 `review.status` 하나로 시작한다. 이 상태는 **등록된 판본과 현재 claims·근거 연결의 원문 검토 상태**이며, 논문 전체의 진실성·독립 재현·사용자 이해·프로젝트 채택을 뜻하지 않는다.

- `draft`: 현재 기록의 원문 대조가 아직 완료되지 않음. 필요하면 reason 한 문장으로 남긴다.
- `source-checked`: 현재 등록한 주장·근거·조건을 해당 판본에서 확인했고 확인 범위·날짜·주체 기록이 있음.
- `needs-recheck`: 이미 확인한 내용의 판본·주장·locator가 바뀌거나 근거 불일치가 발견됨. 이전 이력은 유지한다.

이전 확인 이력은 본문의 짧은 항목으로 남긴다: **언제 / 누가 / 어떤 판본의 어느 범위 / 원래 기록 링크**. 복사·형식 변환은 새 확인 이력이 아니다. 과거 검토 이력이 있어도 변경한 주장-locator 대응을 아직 대조하지 않았다면 draft로 남길 수 있다.

반대로 판본·주장·근거 연결이 그대로이고 기존 확인 범위가 분명하면 이력을 이어 쓸 수 있다. 매 조회나 문구 정리 때마다 전체 논문을 다시 읽도록 만들지 않는다. 새 주장·수치·방법·상충 내용 또는 판본 변경이 있을 때 필요한 부분으로 돌아간다. 사람의 검토 버튼만으로 새 원문 확인을 생성하지 않는다.

이력을 옮기는 과정에서 누가/어디까지 확인했는지 알 수 없으면 그 항목을 미확인으로 남긴다. 상태 필터는 구조화 필드, 이력의 상세 독해는 Markdown으로 처리한다. 작성 상태와 원문 상태를 혼동하지 않도록 이전 record_status는 이 최소 예시에서 제거했다. Application의 proposed/accepted는 별도 의사결정 상태로 남긴다.

## 최소 단위

| 단위 | 보존할 내용 | 소유 위치 |
| --- | --- | --- |
| Paper | ID, 제목, 원문 URL, 정확한 판본, 확인일/범위, 가능한 해시 | papers/<id>.md |
| Claim + Evidence | 주장 ID·요지, 근거 ID, PDF 페이지·절·표·그림, 적용 조건·한계 | 해당 Paper 문서 |
| Project | ID, 현재 질문, 조건 정본 참조·확인 시점 | projects/<id>/project.md |
| Application | 카드 ID, 프로젝트/주장/근거 참조, 일치·불일치 조건, 판단·이유, 기존 실험 링크, 다음 확인 | 프로젝트 applications |
| Relation | source/target ID, 관계 종류, 이유, 근거 참조, 작성 주체·확인 상태 | relations.yaml |

Claim/Evidence는 논문 파일 안의 식별 가능한 항목으로 시작한다. 항목마다 독립 파일·DB 테이블을 요구하지 않는다. 논문 사실을 수정할 때 프로젝트별 판단을 자동으로 사실처럼 갱신하지 않는다.

## 상태를 섞지 않기

출처 검토: draft / source-checked / needs-recheck. 내용 종류: 저자 보고 / AI 해석 / 프로젝트 관찰. 적용 판단: apply / adapt / test / defer와 proposed / accepted를 별도로 기록한다. accepted는 실제 결정 근거가 있을 때만 사용한다. 사람 이해·논문 재현 여부는 이 상태에서 추론하지 않는다.

관계 종류의 초기 후보는 cites, evaluates, applies-to, condition-difference다. cites는 실제 인용 근거, applies-to와 condition-difference는 설명과 근거를 가진 분석자 연결이다. contradiction은 같은 조건에서 상반된 결과를 확인하기 전에는 만들지 않는다.

## 사용처별 조건

- 연구 비교: 질문, 방법, 질의/문서 모집단, 평가 분할, metric·분모, 비교군, 연구 제안과 미확인.
- 실험 조언: 과제, 모델·실행 모드, 정확한 입력/출력 제약, 개입, 기존 성공·실패, 외부 평가 결과와 로컬 추론의 구분.
- 공통 조건 필드에 필요한 차원만 채운다. 모든 카드에 모델·학습·실험 항목을 의무화하지 않는다. 미기재는 unknown으로 남기며 같은 조건이라고 추정하지 않는다.

## 검증할 계약

스키마 검사는 구조·ID 참조·필수 locator·상태 조합을 확인한다. 논문의 주장이 참인지, URL 내용이 근거를 지지하는지, 연구가 새로운지를 자동 보증하지 않는다. 조회 권한이 없는 경로는 미확인으로 남긴다.

두 카드의 왕복 보존, 같은 논문의 두 프로젝트 적용, 원문 판본 변경, 끊어진 근거 참조, 카드에 없는 질문의 원문 복귀를 PTP-001과 이후 평가에 연결한다. 정답은 평가자가 관리하고 agent 입력 묶음에 넣지 않는다.

## 구조화와 본문의 경계 — 2026-10-21 검토안

상태: 초기 설계 검토안이다. 이 절의 Evidence·판본 모델 등은 현재 draft-2 필드와 다르며 향후 확장 참고로 보존한다. 실제 실행 형식은 위 최소안과 schema를 따른다.

판단 기준은 **프로그램이 식별·연결·필터·검사해야 하는 정보는 필드로, 사람이 읽으며 판단할 설명은 본문으로**다. 구조화된 필드의 값도 자연어일 수 있다. 단순 문자열과 모든 의미를 코드로 분류하는 것은 다르다.

| 정보 | 저장 제안 | 필요한 동작·이유 |
| --- | --- | --- |
| 문서 ID·종류·schema_version | 공통 필드 | 참조·검사·향후 형식 변경. 논문 버전이나 카드 수정 번호와 구분 |
| 논문 제목·식별자·원문 URL·판본 | Paper 필드 | 동일 논문 연결과 확인한 판본 추적. 논문 전체 ID와 특정 원문 판본을 혼동하지 않음 |
| 주장 ID·짧은 요지·내용 종류 | Paper의 claims 항목 | 주장 단위 선택과 저자 보고/AI 해석 구분. 긴 방법 설명까지 필드로 쪼개지 않음 |
| 근거 ID·판본 참조·원문 위치 | Paper의 evidence 항목 | 주장과 근거의 다대다 연결. 링크 존재와 내용 확인은 별도 |
| 검토 상태·확인일·주체·확인 범위 | 해당 출처/근거의 review 항목 | 카드 전체의 단일 확인 표시가 모든 주장의 검증처럼 보이지 않게 함. 범위 설명은 자연어 허용 |
| 프로젝트·주장/근거 참조·조건 정본 링크 | Application 필드 | 프로젝트 전환과 원문 역추적. 외부 링크는 기준 위치를 명시하고 이동 후 의미가 바뀌지 않게 함 |
| 적용 방향·제안/채택 여부 | Application의 decision 항목 | 적용 방향과 의사결정 상태를 분리. 원문에 방향이 없으면 미정으로 남기고 자동 추론하지 않음 |
| 방법의 상세·조건 차이·해석·한계·판단 이유·다음 실험 설명 | 해당 Paper/Application의 Markdown 본문 | 의미 손실 없이 문장·수식·표 보존. 출력에 함께 포함해야 할 내용 |
| 반복 비교할 실험 조건 | 실제 질의가 필요한 일부만 후속 구조화 | 모델·평가 분할·지표가 모든 논문의 필수 필드는 아님. 구조화 전에는 해당 조건을 자동 비교할 수 있다고 약속하지 않음 |
| 상세 수치·수식·복잡한 결과표 | 우선 본문과 원문 locator | 수치 필드가 필요해지면 값·단위·분모·조건·출처를 한 묶음으로 설계. 숫자만 추출하지 않음 |
| 기존 실험의 상세·정답·사이트 결과 | 기존 프로젝트 정본을 참조 | 원본 복제와 낡은 이중 기록 방지. 링크 대상을 자동 업로드하지 않음 |

필수 입력을 처음부터 모두 강제하지 않는다. 초안은 불완전한 상태로 저장할 수 있고, 검토된 근거로 내보낼 때 누락을 알리는 단계를 구분한다. 필드 누락은 false·0·없음이 아니며 미확인이다. 거대한 자유 확장 객체를 먼저 만들기보다 실제로 필요한 조건부터 추가한다.

## 원문 위치와 본문 연결

원문 locator는 `pdf_page`(파일의 1부터 시작하는 페이지), `printed_page`(인쇄면 문자열), `section`, `table`, `figure`처럼 구별하는 안을 검토한다. 실제 근거가 있는 항목만 채우며 복수 위치는 배열로 보존한다. “PDF pp.1–2, §4.2”라는 기록만으로 §4.2가 p.1–2에 있다고 합치지 않는다. 둘은 별도 locator이며 연결 관계는 원문에서 확인해야 한다.

Paper의 단일 URL과 해시만으로 여러 판본을 덮어쓰지 않는다. evidence가 어느 판본을 가리키는지 유지하고 변경 시 재검토 대상으로 표시한다. 판본 객체의 정확한 형태는 후속이다.

본문을 필드와 별도로 손으로 요약·복제하는 이중 정본은 피한다. 짧은 주장 요지는 구조화 항목에 한 번 두고, 상세 설명은 본문이 소유한다. 제목·상태·서지는 UI에서 필드로부터 표시할 수 있다. 원래 본문을 보존한 초기 변환물에 중복이 남으면 이를 표시하고 자동 삭제하지 않는다.

첫 agent 내보내기는 선택 Application과 연결된 Paper의 **필드와 본문을 함께** 포함하는 보수적 방식을 검토한다. 조건·한계·미확인을 생략한 주장만의 내보내기를 기본값으로 삼지 않는다. 분량 때문에 생략하면 생략 범위와 원본 위치를 명시한다. 이후 주장별 본문 분할이 필요하면 안정적인 절 식별자·참조 무결성·누락 검사를 먼저 정한다. 제목 자동 anchor가 안정 계약이라고 가정하지 않는다.

2026-10-21에 공식 문서와 공개 소스의 해당 구조를 읽었다. 움직이는 branch의 관찰이며 버전 고정·라이선스 채택·실행 검증이 아니다. PaperQA는 이번 조회에서 타입 소스 경로를 확인하지 못해 데이터 모델 비교 근거에서 제외했다. 이전의 실행 기능 소개와 구분한다.

## 다음 작은 결정

초기 개인 카드의 분리 예시와 대조 기록은 로컬에 보존한다. 공개 재현에는 schema와 합성 예제를 사용한다. 현재 읽기·내보내기의 보존과 이후 편집·저장 왕복 검증을 구분하며 AI의 대조만으로 사용자 이해·연구 효과를 확정하지 않는다.

## 기록 단위와 화면 모양의 구분

“카드”는 초기 작업명이며 사각형 타일 UI나 짧은 고정 길이를 의미하지 않는다. Paper는 논문 기록, Application은 프로젝트 적용 노트로 이해할 수 있다. 저장은 구분하되 사용자 화면과 agent 출력에서는 연결된 내용을 한 읽기 묶음으로 제공할 수 있다.

가시성은 미검증이다. 특정 항목 찾기는 목록, 같은 축 비교는 표, 조건·근거 독해는 문서형 상세가 적합하다는 가설부터 검토한다. 카드 타일은 소수 항목의 요약 탐색에 유용할 수 있지만 긴 한계를 숨기거나 항목별 정보 위치가 달라 비교 부담을 만들 수 있다([NN/G](https://www.nngroup.com/articles/cards-component/)). [Zotero](https://www.zotero.org/support/sorting)의 정렬 가능한 목록은 참고 사례이며 우리 제품의 효과 증거가 아니다. 데이터 분리와 화면 선택을 서로의 채택 근거로 순환시키지 않는다.
